# dft v2 Redesign — Implementation Plan

> **For Hermes:** Use subagent-driven-development skill to implement this plan task-by-task.

**Goal:** Redesign dft from a monolithic fire-and-forget pipeline into four contract-driven phases. Intent and Solution run as Hermes agents with skills (no CLI). Orchestration and Evaluation run as deterministic Go engine CLI commands. Each phase consumes a well-defined contract from the previous phase and produces a contract for the next.

**Architecture:**

```
┌─────────────────────────────────────────────────────────┐
│          PHASE 1: INTENT  (Hermes agents + skills)      │
│  Raw demand → DemandPackage.json                        │
│  Agents: ambiguity-scanner → demand-refiner → ac-verifier│
│  Output: .dft/runs/<id>/intent/demand-package.json      │
├─────────────────────────────────────────────────────────┤
│         PHASE 2: SOLUTION  (Hermes agents + skills)     │
│  DemandPackage → SolutionDesign.json                    │
│  Agents: test-planner → wbs-author → surface-contract   │
│  Output: .dft/runs/<id>/design/solution-design.json     │
├─────────────────────────────────────────────────────────┤
│       PHASE 3: ORCHESTRATION  (dft build CLI)           │
│  SolutionDesign → Chunk dispatch → Code on increment    │
│  Engine: deterministic dispatcher + executor registry   │
│  Executors: speckit, direct-implement, stub             │
│  Output: increment branch + orchestration-result.json   │
├─────────────────────────────────────────────────────────┤
│       PHASE 4: EVALUATION  (dft evaluate CLI)           │
│  Code + TestPlan + Eval surfaces → Verdict              │
│  Engine: readiness → BDD eval → verdict                 │
│  Output: evaluation.json + evidence                     │
└─────────────────────────────────────────────────────────┘
```

**Tech Stack:** Go (CLI engine + domain types), Hermes skills + agent prompts (intent/solution phases), SQLite state store, existing BDD eval framework.

**Driving model:** The user works entirely inside Hermes. "Help me design a CLI tool for..." triggers intent/solution agents. "Save the demand package" persists the contract to disk. "Build it" calls `dft build`. "Evaluate it" calls `dft evaluate`. The dft CLI only exists for phases 3-4 — phases 1-2 run as Hermes agent interactions.

## Domain Contracts (v2)

These are the JSON contract schemas that hand off between phases. Both agents (writing) and CLI commands (reading) conform to these.

### Intent → Solution: `DemandPackage`

Written by intent agents, saved to `.dft/runs/<run-id>/intent/demand-package.json`.

```go
type DemandPackage struct {
    ID                 string              `json:"id"`
    Title              string              `json:"title"`
    RawDemand          string              `json:"raw_demand"`
    RefinedDemand      string              `json:"refined_demand"`
    AcceptanceCriteria []AcceptanceCriterion `json:"acceptance_criteria"`
    Assumptions        []string            `json:"assumptions"`
    NonGoals           []string            `json:"non_goals"`
    Ambiguities        []AmbiguityFinding   `json:"ambiguities"`
    VerifiedComplete   bool                `json:"verified_complete"`
    CreatedAt          time.Time           `json:"created_at"`
}

type AcceptanceCriterion struct {
    ID          string `json:"id"`
    Description string `json:"description"`
    Requirement string `json:"requirement,omitempty"`
}

type AmbiguityFinding struct {
    ID          string `json:"id"`
    Description string `json:"description"`
    Resolution  string `json:"resolution,omitempty"`
}
```

### Solution → Orchestration: `SolutionDesign`

Written by solution agents, saved to `.dft/runs/<run-id>/design/solution-design.json`. Uses the **existing** WBS and LaneAssignment schemas from `internal/domain/wbs.go`.

```go
// SolutionDesign is the full contract output of the Solution phase.
type SolutionDesign struct {
    DemandPackageID     string              `json:"demand_package_id"`
    TestPlan            TestPlan            `json:"test_plan"`
    WBS                 WBS                 `json:"wbs"`                  // existing schema
    LaneAssignments     []LaneAssignment    `json:"lane_assignments"`     // existing schema
    EvalSurfaceContract EvalSurfaceContract `json:"eval_surface_contract"`
    CreatedAt           time.Time           `json:"created_at"`
}

// TestPlan — NEW type for v2.
type TestPlan struct {
    DemandPackageID string         `json:"demand_package_id"`
    RequirementIDs  []string       `json:"requirement_ids"`
    Scenarios       []TestScenario `json:"scenarios"`
}

type TestScenario struct {
    ID             string   `json:"id"`
    Name           string   `json:"name"`
    RequirementIDs []string `json:"requirement_ids"`
    Description    string   `json:"description"`
    Given          []string `json:"given"`
    When           []string `json:"when"`
    Then           []string `json:"then"`
}

// EXISTING — from internal/domain/wbs.go — reused as-is.
// WBS is the append-only work breakdown structure.
type WBS struct {
    DemandPackageID string    `json:"demand_package_id"`
    Specs           []SpecRef `json:"specs"`
}

// SpecRef identifies one independently executable spec.
type SpecRef struct {
    ID                 string   `json:"id"`
    Description        string   `json:"description"`
    PromptPath         string   `json:"prompt_path,omitempty"`
    AcceptanceCriteria []string `json:"acceptance_criteria"`
}

// LaneAssignment binds a spec to a lane selected for execution.
type LaneAssignment struct {
    SpecID    string `json:"spec_id"`
    Lane      string `json:"lane"`
    Rationale string `json:"rationale"`
}
```

### Orchestration → Evaluation: `OrchestrationResult`

Written by `dft build`, saved to `.dft/runs/<run-id>/orchestration-result.json`.

```go
type OrchestrationResult struct {
    DemandPackageID  string           `json:"demand_package_id"`
    IncrementBranch  string           `json:"increment_branch"`
    SpecResults      []SpecResult     `json:"spec_results"`
    ArtifactManifest ArtifactManifest `json:"artifact_manifest"`
    CompletedAt      time.Time        `json:"completed_at"`
}

type SpecResult struct {
    SpecID      string        `json:"spec_id"`
    Lane        string        `json:"lane"`       // which lane (executor) ran
    Status      string        `json:"status"`     // "completed" | "failed" | "skipped"
    Branch      string        `json:"branch"`
    Artifacts   []ArtifactRef `json:"artifacts"`
    Transcripts []string      `json:"transcripts"`
    Findings    []Finding     `json:"findings,omitempty"`
}
```

## Task 2: Define the executor interface (pluggable execution plans)

**Objective:** Create an interface that multiple execution plans (Speckit, direct-implement, stub) can implement, replacing the hardcoded Speckit-only lane.

**Files:**
- Create: `internal/orchestration/v2/executor.go`

```go
package v2

import (
    "context"
    "github.com/bocacorazon/dft/internal/domain"
    "github.com/bocacorazon/dft/internal/domain/v2"
    "github.com/bocacorazon/dft/internal/ports"
)

// Executor runs one spec using a specific lane (execution plan).
// Lane names map directly to executors: "speckit" → SpeckitExecutor, "direct" → DirectExecutor, etc.
type Executor interface {
    // Name returns the lane name this executor handles.
    Name() string

    // Execute runs one spec and returns the result.
    Execute(ctx context.Context, input ExecutorInput) (v2.SpecResult, error)
}

type ExecutorInput struct {
    Spec            domain.SpecRef
    RunID           string
    IncrementBranch string
    WorktreePath    string
    Agent           ports.AgentAdapter
    ArtifactRoot    string
}

type ExecutorRegistry struct {
    executors map[string]func() Executor
}

func NewExecutorRegistry() *ExecutorRegistry {
    return &ExecutorRegistry{executors: make(map[string]func() Executor)}
}

func (r *ExecutorRegistry) Register(name string, ctor func() Executor) {
    r.executors[name] = ctor
}

func (r *ExecutorRegistry) Get(name string) (Executor, bool) {
    ctor, ok := r.executors[name]
    if !ok { return nil, false }
    return ctor(), true
}
```

## Task 3: Implement the spec dispatcher

**Objective:** Build the deterministic orchestration engine. Reads WBS specs + lane assignments, selects executors from the registry, dispatches specs in order, collects results. No agent judgment involved — pure engine logic. Specs are executed sequentially (the existing WBS has no dependency graph; parallelism is a future enhancement).

**Files:**
- Create: `internal/orchestration/v2/dispatcher.go`
- Create: `internal/orchestration/v2/dispatcher_test.go`

**Key behavior:**
- Iterates WBS.Specs in order
- For each spec, looks up lane assignment → maps lane name to executor via registry
- Calls `executor.Execute()` for each spec
- Fail-fast: stops on first spec failure
- Returns `OrchestrationResult` on success, partial results + error on failure
- Error on unknown lane (no executor registered for that lane name)

**Tests to write:**
- Single spec dispatch (with stub executor, lane "stub")
- Multi-spec sequential dispatch
- Unknown lane error
- Fail-fast on spec failure (second spec not executed after first fails)

**Commit:**
```bash

git commit -m "feat: implement deterministic spec dispatcher with lane-to-executor mapping"
```

## Task 6: Create intent-phase Hermes skills and agent prompts

**Objective:** Build three Hermes agent skills that handle the Intent phase. These are NOT Go code — they are skill documents that Hermes loads when the user says "help me design/refine this."

**Files:**
- Create: `.dft/skills/intent/ambiguity-scanner/SKILL.md`
- Create: `.dft/skills/intent/demand-refiner/SKILL.md`
- Create: `.dft/skills/intent/ac-verifier/SKILL.md`
- Create: `.dft/skills/intent/README.md`

### ambiguity-scanner skill

Scans raw demand for:
- Unclear or ambiguous terms ("fast", "secure", "good UX")
- Missing context (target platform, scale expectations, constraints)
- Conflicting statements
- Implicit assumptions that should be made explicit

Outputs a list of `AmbiguityFinding` entries. Each finding has an ID, description, and suggested resolution. The user can answer inline, and the scanner re-checks.

### demand-refiner skill

Takes raw demand + ambiguity findings (with resolutions) and produces:
- `RefinedDemand`: a clear, unambiguous statement of what to build
- `AcceptanceCriteria`: atomic, testable, observable behaviors
- `Assumptions`: what's being assumed about the environment
- `NonGoals`: explicit scope boundaries

### ac-verifier skill

Checks the acceptance criteria:
- Every requirement in the refined demand has at least one AC
- Every AC is atomic, testable, and describes observable behavior
- No AC is vague or circular
- Sets `VerifiedComplete: true` only when all checks pass

If gaps found, returns findings. Hermes loops refiner → verifier until clean.

**Output format:** Each skill document describes what the agent receives, what it produces, and the JSON schema it must conform to. The agent writes directly to `.dft/runs/<run-id>/intent/demand-package.json`.

## Task 7: Create solution-phase Hermes skills and agent prompts

**Objective:** Build three Hermes agent skills for the Solution phase. These consume the DemandPackage and produce the SolutionDesign.

**Files:**
- Create: `.dft/skills/solution/test-planner/SKILL.md`
- Create: `.dft/skills/solution/wbs-author/SKILL.md`
- Create: `.dft/skills/solution/surface-contract-author/SKILL.md`
- Create: `.dft/skills/solution/README.md`

### test-planner skill

Reads the DemandPackage (specifically acceptance criteria, refined demand, assumptions, non-goals). Produces a `TestPlan` with Gherkin-style scenarios. Each scenario links to an acceptance criterion. The planner must not see implementation code — it's a pure requirements-to-behavior mapping.

### wbs-author skill

Reads the DemandPackage + TestPlan. Produces a `WBS` with `SpecRef`s and `LaneAssignment`s using the **existing schemas from `internal/domain/wbs.go`**. Each spec:
- Has a unique ID, description, and acceptance criteria
- Optional `prompt_path` for prompt files stored alongside the spec
- Gets a lane assignment (lane = executor name) with rationale

The WBS must cover all test plan scenarios (traceability from scenarios to spec acceptance criteria).

### lane-assignment skill

Reads the WBS and selects a lane for each spec. Lanes map to executors: `"speckit"` → full specify/plan/tasks/analyze/implement/review/mergeback pipeline; `"direct"` → single implement pass; `"stub"` → no-op for smoke testing. Each assignment includes a rationale.

### surface-contract-author skill

Reads the DemandPackage, WBS, and artifact references. Produces the `EvalSurfaceContract` declaring what observable surfaces will exist for evaluation (CLI, HTTP API, file outputs, etc.).

### solution-design assembler

The three agents above run sequentially within Hermes. A simple assembly step combines their outputs into `solution-design.json`. The WBS author's coverage is verified against the test plan scenarios automatically.

**Output:** `.dft/runs/<run-id>/design/solution-design.json`

## Task 8: Implement the `dft build` CLI command

**Objective:** The `dft build` command reads `solution-design.json`, creates the increment branch, dispatches specs via the spec dispatcher, and writes `orchestration-result.json`.

**Files:**
- Modify: `internal/app/cli.go` (add `build` command)
- Create: `internal/app/build_command.go`

**Command:**

```
dft build <run-id>              # Dispatch all specs per lane assignments
dft build <run-id> --spec <id>  # Execute a single spec in isolation
dft build <run-id> --resume     # Resume from last incomplete spec
dft build status <run-id>       # Show per-spec execution status
```

**Behavior:**
1. Read `.dft/runs/<run-id>/design/solution-design.json`
2. Validate the SolutionDesign (WBS + LaneAssignments)
3. Create increment branch from default branch
4. Load executor registry (speckit, direct, stub registered)
5. Run Dispatcher.Dispatch() with WBS.Specs + LaneAssignments
6. Write `.dft/runs/<run-id>/orchestration-result.json`
7. Print summary: N/N specs complete, any failures

**Single-spec mode:** `--spec <id>` executes only that spec (skips others). Useful for debugging.

**Resume mode:** `--resume` reads `orchestration-result.json`, finds first incomplete spec, picks up from there.

**Commit:**
```bash

git commit -m "feat: add dft build command with spec dispatcher"

```


**Behavior:**
1. Read `orchestration-result.json` + `solution-design.json`
2. Run readiness: surface-to-artifact binding + probes
3. Run eval-plan author: produce BDD scenarios from TestPlan
4. Run eval executor: execute scenarios, collect evidence
5. Write `.dft/runs/<run-id>/eval/evaluation.json`

If eval fails, automated remediation loop (up to retry limit) runs before returning final verdict. Exhausted retries → escalate to `.dft/inbox/`.

## Key Design Decisions

1. **Intent and Solution are Hermes skills, not CLI commands** — no `dft intent`, no `dft solution`. The user types "help me design this" in Hermes, agents run, contracts are saved to disk.

2. **Build and Evaluate are deterministic CLI commands** — `dft build` and `dft evaluate` are Go engine code that Hermes calls via `terminal()`.

3. **Contracts are plain JSON on disk** — agents write them, CLI reads them. No shared Go process needed between agent phases and engine phases.

4. **Executors are pluggable** — Speckit is one option; direct-implement, stub, and future plans are peers in a registry.

5. **Dispatcher is deterministic** — specs are executed sequentially in WBS order, mapped to executors via lane assignments. Engine logic only, no agent judgment. (Dependency-graph parallelism is a future enhancement on the existing WBS schema.)

6. **Specs and lanes use existing schemas** — `internal/domain/wbs.go` already defines `SpecRef`, `WBS`, and `LaneAssignment`. The solution agents produce these; the build command consumes them. No new types needed for the WBS contract.

7. **Gates are automated within phases** — ac-verifier loops in Intent, code-review loops in Speckit executor, eval loops in Evaluate. Hermes inspects outputs and decides to proceed.

8. **Artifacts saved on user confirmation** — Hermes shows the draft demand package / solution design, user says "save it," then the contract is written to `.dft/runs/<run-id>/`.

9. **Test plan is authored alongside WBS** — evaluation is designed before code exists, not retrofitted.
